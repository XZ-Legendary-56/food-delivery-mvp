## 1. Что это

Модульный монолит на Go: каталог заведений и меню, корзина и оформление
заказа с защитой от гонок за остатки, партнёрский API для самих заведений, доставка
событий вебхуком с ретраями, и отдельный вымышленный сервис-заведение, эмулирующий
интеграцию с реальным рестораном. Отдельная фишка площадки — «Спасение остатков»:
заведения продают со скидкой то, что иначе к концу дня спишут в ноль.

Два входа: публичный API для клиентов (без регистрации, анонимно) и партнёрский —
для заведений, закрытый статическим API-ключом.

## 2. Быстрый старт

### 2.1. Что нужно установить

Только **Docker** и **Docker Compose** (идут вместе в Docker Desktop на Windows/macOS;
на Linux — `docker` + плагин `docker-compose-plugin`). Больше ничего — ни Go, ни
PostgreSQL на хосте ставить не нужно, всё собирается и запускается внутри контейнеров.

Проверить, что всё установлено и Docker-демон запущен:

```bash
docker --version          # Docker version 24+ (проверено на 27+)
docker compose version    # Docker Compose version v2+
docker info                # не должно быть ошибки "cannot connect to the Docker daemon"
```

### 2.2. Клонирование и запуск

```bash
git clone <URL этого репозитория>
cd food-delivery-mvp
docker compose up --build
```

Это **единственная команда**, которая нужна. Переменные окружения (`.env.example`)
опциональны — без них подставятся дефолты, зашитые прямо в `docker-compose.yml`.

Compose поднимает по очереди: `postgres` (с healthcheck `pg_isready`) → `migrator`
(применяет миграции и завершается) → `seed` (грузит демо-данные и завершается) → `api`
(ждёт готовности БД, сам отвечает на `/readyz`) → `swagger-ui` и `venue-pasta-roma`
(оба ждут, пока `api` пройдёт healthcheck). Порядок держится на `depends_on` с
условиями `service_healthy` / `service_completed_successfully` — руками ничего
дожидаться не нужно, `docker compose up` вернёт управление, когда всё уже готово.

**Сколько это занимает.** На прогретом кэше сборки (базовые образы Go/Postgres/nginx
уже скачаны) — около **1–1.5 минут** до полной готовности всех сервисов. При самом
первом запуске на чистой машине Docker дополнительно скачает базовые образы
(`golang`, `postgres:16-alpine`, `swaggerapi/swagger-ui`) — это может добавить ещё
несколько минут в зависимости от скорости интернета.

Логи любого сервиса — `docker compose logs -f api` (или `make logs` для всех сразу).

### 2.3. Куда смотреть

| Сервис | Адрес | Что это |
|---|---|---|
| API | http://localhost:8080 | Публичный `/api/v1/...` и партнёрский `/api/v1/partner/...` |
| **Swagger UI** | **http://localhost:8081** | Обе спеки сразу, переключаются выпадающим списком в шапке страницы («Public API» / «Partner API»). «Try it out» работает по-настоящему — бьёт на порт 8080, CORS настроен именно для этого |
| Сервис-заведение | http://localhost:8090 | `venue-pasta-roma` — своя лента кухни `GET /kitchen/orders`, приём вебхуков |
| PostgreSQL | localhost:5434 | Наружу пробрасывается на нестандартный порт — 5432/5433 часто заняты локальной установкой Postgres |

`/healthz` и `/readyz` у `api` — обычные проверки живости/готовности, ими же
пользуется Docker-healthcheck.

### 2.4. Полный сценарий заказа — curl'ом от начала до конца

Демо-данные фиксированные (сиды используют одни и те же UUID при каждом запуске),
поэтому команды ниже можно копировать одну за другой ровно как есть — сработает
на только что поднятой системе. `X-Client-Id` клиент придумывает сам (это любой
UUID, тут просто константа для повторяемости примера).

```bash
CLIENT_ID="11111111-1111-1111-1111-111111111111"

# 1. Список заведений
curl -s http://localhost:8080/api/v1/venues | jq

# 2. Меню «Пицца Мания» (её id зафиксирован сидами)
VENUE_ID="00000000-0000-0000-0000-000000000011"
curl -s http://localhost:8080/api/v1/venues/$VENUE_ID/menu | jq

# 3. Кладём в корзину пиццу «Пепперони» (её id тоже из сидов) и колу
curl -s -X POST http://localhost:8080/api/v1/cart/items \
  -H "X-Client-Id: $CLIENT_ID" -H "Content-Type: application/json" \
  -d '{"menuItemId":"00000000-0000-0000-0000-000000000032","quantity":1}' | jq

curl -s -X POST http://localhost:8080/api/v1/cart/items \
  -H "X-Client-Id: $CLIENT_ID" -H "Content-Type: application/json" \
  -d '{"menuItemId":"00000000-0000-0000-0000-000000000034","quantity":1}' | jq

# 4. Смотрим собранную корзину
curl -s http://localhost:8080/api/v1/cart -H "X-Client-Id: $CLIENT_ID" | jq

# 5. Оформляем заказ. Idempotency-Key обязателен — повтор с тем же ключом
#    и тем же телом просто вернёт тот же заказ, а не создаст дубль.
curl -s -X POST http://localhost:8080/api/v1/orders \
  -H "X-Client-Id: $CLIENT_ID" -H "Content-Type: application/json" \
  -H "Idempotency-Key: demo-order-1" \
  -d '{"deliveryAddress":"Moscow, Tverskaya st, 1","customerPhone":"+79990000000","comment":"door code 123"}' | jq

# Возьмите "id" заказа из ответа выше и подставьте в ORDER_ID
ORDER_ID="<id из предыдущего ответа>"

# 6. Смотрим статус и историю переходов
curl -s http://localhost:8080/api/v1/orders/$ORDER_ID -H "X-Client-Id: $CLIENT_ID" | jq

# 7. Отменяем (сработает, пока заведение не начало готовить)
curl -s -X POST http://localhost:8080/api/v1/orders/$ORDER_ID/cancel -H "X-Client-Id: $CLIENT_ID" | jq
```

Каждый шаг реально проверен на поднятой системе перед тем, как попасть в этот README.
`jq` нужен только для красивого вывода — без него команды тоже отработают, просто
ответ придёт одной строкой JSON.

**Конфликтный сценарий за один запрос** — заказ на сумму меньше минимального чека:

```bash
CLIENT_ID2="44444444-4444-4444-4444-444444444444"
curl -s -X POST http://localhost:8080/api/v1/cart/items \
  -H "X-Client-Id: $CLIENT_ID2" -H "Content-Type: application/json" \
  -d '{"menuItemId":"00000000-0000-0000-0000-000000000034","quantity":1}' > /dev/null

curl -s -X POST http://localhost:8080/api/v1/orders \
  -H "X-Client-Id: $CLIENT_ID2" -H "Content-Type: application/json" \
  -H "Idempotency-Key: demo-order-2" \
  -d '{"deliveryAddress":"Moscow, Tverskaya st, 1","customerPhone":"+79990000000"}' | jq
# → 422, code: MIN_ORDER_AMOUNT_NOT_REACHED, в теле — сколько не хватает
```

### 2.5. Партнёрский API

Ключи выданы демо-сидами (видны и в логе `docker compose logs seed`):

| Заведение | `X-Api-Key` |
|---|---|
| Пицца Мания | `demo_pizza_mania_2026` |
| Токио Вок | `demo_tokyo_wok_2026` |
| Бургерная №1 | `demo_burger_house_2026` |
| Pasta Roma (интегрированное, см. ниже) | `demo_pasta_roma_2026` |

```bash
# Свой профиль заведения
curl -s http://localhost:8080/api/v1/partner/venue -H "X-Api-Key: demo_pizza_mania_2026" | jq

# Новые заказы (поллинг — тот же способ, каким пользуется venue-pasta-roma)
curl -s "http://localhost:8080/api/v1/partner/orders?status=created" \
  -H "X-Api-Key: demo_pizza_mania_2026" | jq

# Принять заказ (ORDER_ID — из предыдущего вызова)
curl -s -X POST http://localhost:8080/api/v1/partner/orders/$ORDER_ID/accept \
  -H "X-Api-Key: demo_pizza_mania_2026" -H "Content-Type: application/json" \
  -d '{"etaMinutes":30}' | jq
```

Заведение «Pasta Roma» — особый случай: это интегрированное заведение, за него всё
проделывает отдельный сервис `venue-pasta-roma` (порт 8090) полностью автоматически
— само грузит меню, само принимает и продвигает заказы по статусам. Закажите что-нибудь
у Pasta Roma и последите: `GET /api/v1/orders/{id}` дойдёт до `delivered` сам, без единого
ручного вызова партнёрского API — на демонстрационных интервалах это занимает секунд 30-40.

### 2.6. Остановить и почистить

```bash
docker compose down -v
```
`-v` удаляет volume с данными Postgres — следующий `docker compose up` стартует с
чистой демо-базой.

## 4. Архитектура

### 4.1. Модульный монолит

Одно приложение, одна база, четыре модуля с жёсткими границами: `catalog` (заведения,
меню, остатки), `order` (корзина, заказы, стейт-машина), `partner` (партнёры и ключи),
`outbox`/`integration` (исходящие события).

**Почему не микросервисы сразу.** Цель — готовность к масштабированию, а не
распределённость сама по себе — это разные вещи. Вся настоящая техническая сложность
здесь сосредоточена в одном месте: **атомарном списании остатка при оформлении
заказа**. Два клиента одновременно берут последнюю порцию — ровно один должен
выиграть, второй должен узнать об этом сразу и честно, а не после того, как оба
решили, что заказ прошёл.

В монолите с одной базой это решается одним `SELECT ... FOR UPDATE ORDER BY id` внутри
одной транзакции (раздел 10) — Postgres сам не пускает вторую транзакцию читать
заблокированную строку, пока первая не закоммитится или не откатится. Код этой
проверки — несколько десятков строк, и ошибиться в нём почти невозможно: либо
транзакция целиком применилась, либо целиком откатилась.

Если разрезать `catalog` и `order` на два сервиса с двумя базами прямо сейчас, эта
транзакция физически исчезает — между двумя базами нет общего ACID. Атомарное списание
пришлось бы заменять сагой: резервирование остатка с TTL, отдельный фоновый процесс,
который освобождает зависшие резервы (что делать, если сервис заказов упал ровно между
резервированием и подтверждением?), компенсирующие операции на каждый вид сбоя, свой
outbox уже в двух сервисах вместо одного, и контрактные тесты, чтобы два независимо
деплоящихся сервиса не разъехались по формату сообщений. Это не эстетическое
предпочтение — это примерно вдвое больше кода, и почти весь прирост инфраструктурный,
а не про сам домен доставки еды.

При этом настоящая распределённая задача в проекте есть и решена по-настоящему:
интеграция с сервисом-заведением (раздел 8) — это независимый процесс, разговаривающий
только по контракту, с честной моделью at-least-once, идемпотентностью на приёме и
ретраями. Просто эта граница проходит не между `catalog` и `order` (где она стоила бы
дороже всего), а там, где она и так естественна — между платформой и внешней системой
заведения, у которых изначально нет и не может быть общей базы.

**Границы проверяются линтером, а не обещанием.** `depguard` в `.golangci.yml` не даёт
`domain` зависеть от `usecase`/`adapter`, не даёт одному `usecase/<module>` пакету
импортировать другой, не даёт адаптерам знать друг о друге — эти правила падают в CI
на каждый PR, а не живут в головах разработчиков.

### 4.3. Правила зависимостей

```
domain    → ничего кроме stdlib и google/uuid
usecase   → domain + свои собственные порты (интерфейсы)
adapter/* → usecase + domain + generated; адаптеры не знают друг о друге
модули    → общаются только через публичный <module>/api, internal чужого модуля не импортируется
```

Модули `usecase/catalog`, `usecase/order`, `usecase/partner`, `usecase/outbox` взаимно
изолированы; `adapter/postgres`, `adapter/webhook`, `adapter/http/public`,
`adapter/http/partner` — тоже (кроме `adapter/http` как корня композиции — ему по
определению нужно знать про всех, он их связывает, — и `adapter/http/middleware` +
`adapter/http/httperr`, общей инфраструктуры для обоих HTTP-контуров). Все правила —
это `depguard`-секции `.golangci.yml`, а не только текст этого README.

## 5. Микросервисный вариант

[Целевая схема](docs/img/target-microservices.png) ([исходник](docs/c4/target-microservices.puml))
— как система выглядела бы после разрезания на сервисы, если бы масштаб это оправдал.

**Порядок отделения — не случайный, а по убыванию транзакционной связности с остальным:**

1. **`integration`** — первым. У него уже сейчас нет ни одной общей транзакции с
   `catalog` или `order`: outbox-воркер работает через таблицу событий и HTTP,
   граница между «внутри» и «снаружи» уже проходит ровно там, где нужно.
2. **`catalog`** — вторым. Вот здесь и появляется настоящая цена вопроса: списание
   остатка при оформлении заказа перестаёт быть локальной транзакцией и становится
   сагой между `order-service` и `catalog-service` — `order` резервирует остаток
   HTTP/gRPC-вызовом, `catalog` подтверждает или освобождает резерв, а зависшие
   резервы (сервис упал между шагами) чистит отдельный воркер по таймауту. Это
   единственное место, где распределённость по-настоящему стоит денег.
3. **`partner`** — последним. У него меньше всего связности с горячим путём заказа:
   партнёр меняет своё меню и остатки не в том же запросе, где клиент оформляет заказ.

Брокер сообщений (например Kafka) появляется только на этой целевой схеме — у outbox
здесь наконец есть второй потребитель, `integration-service`, который оправдывает его
существование (раздел 11).

## 6. CJM (карта пути пользователя)

- [CJM клиента](docs/img/cjm-customer.png) ([исходник](docs/cjm/cjm-customer.puml)) — от
  осознания потребности до получения заказа, с отдельной веткой входа через подборку
  «Спасение остатков» и всеми конфликтными сценариями раздела 5.2 прямо на диаграмме.
- [CJM заведения](docs/img/cjm-venue.png) ([исходник](docs/cjm/cjm-venue.puml)) — от
  подключения до завершения заказа, с двумя явно отмеченными точками потери заказов.
- [Стейт-машина заказа](docs/img/order-state-machine.png) ([исходник](docs/cjm/order-state-machine.puml))

**Разбор трудностей клиента** (как человек находит товар и с какими трудностями
сталкивается):

- *Пришёл, а заведение закрыто или не принимает заказы* — узнаёт об этом сразу на
  карточке заведения, а не после сборки корзины; ответ содержит время следующего
  открытия.
- *То, что хотел, кончилось, пока листал меню* — доступность проверяется уже на
  добавлении в корзину («мягкая» проверка), а не только на оформлении.
- *Набрал меньше минимального чека* — ответ прямо говорит, сколько не хватает. Именно
  здесь работает связка с «Спасением остатков»: добор акционной позицией часто дешевле
  закрывает разницу, чем полноценная новая позиция.
- *Два человека одновременно взяли последнюю порцию* — гонка решается в базе
  блокировкой строки; проигравший получает честный `INSUFFICIENT_STOCK` с реальным
  остатком, а не «заказ создан», который потом тихо отменят.
- *Успел добавить акционную позицию, а окно акции закрылось, пока собирал заказ* —
  `RESCUE_OFFER_EXPIRED` с новой ценой и временем окончания в ответе, а не молчаливая
  потеря скидки.
- *Передумал после того, как заведение начало готовить* — честный отказ
  `ORDER_INVALID_STATE_TRANSITION`: отмена уже не бесплатна для заведения, оно уже
  потратило продукты.

**Разбор трудностей заведения:**

- *Вебхук о новом заказе не дошёл* (у заведения моргнула сеть дольше 5 попыток
  доставки) — заказ не теряется полностью: он всё ещё виден поллингом
  `GET /partner/orders`, но заведение узнаёт о нём позже, чем могло бы.
- *Забыли обновить стоп-лист или остаток* — клиент успевает заказать то, чего физически
  уже нет; заведению приходится либо готовить сверх плана, либо отклонять уже принятый
  заказ вручную. Ровно поэтому у `venue-pasta-roma` синхронизация остатков — фоновый
  цикл, а не разовое действие.

## 7. Схема БД

[ERD](docs/img/erd.png) ([исходник](docs/erd.puml)), 14 таблиц, PostgreSQL 16, миграции
`pressly/goose` с рабочим `Down` у каждой (`migrations/`).

### 7.1. Решения, которые стоит объяснять на собеседовании

**Деньги — целым числом копеек (`BIGINT price_minor`), без `NUMERIC` и тем более
`float`.** Дробные типы дают ошибки округления, которые всплывают ровно там, где
дороже всего — при суммировании корзины.

**Название и цена копируются в `order_items` (`name_snapshot`, `unit_price_minor`).**
Заведение может переименовать блюдо или поднять цену завтра — уже оформленный заказ
не должен меняться задним числом. Ссылка на `menu_item_id` при этом остаётся: она
нужна для аналитики и для связи с остатками, снимок и связь решают разные задачи.

**`stock_qty` и `is_available` — два независимых механизма**, не один флаг.
`is_available = false` — заведение выключило позицию руками (стоп-лист).
`stock_qty` — жёсткий счётчик, уменьшается при каждом заказе; `NULL` означает
«количество не ограничено» (типично для блюд, готовящихся под заказ, а не с полки).
Причины недоступности разные, и пользователю правильно показывать их по-разному:
«сегодня не готовим» — это не то же самое, что «осталась одна порция вместо трёх».

**`source` + `external_id` — связь с источником данных** (решает вопрос, как связать
данные в системе с источниками). Позиция, пришедшая из системы
заведения, хранит идентификатор, под которым она известна там. Уникальный индекс
`(venue_id, external_id)` — то, что делает повторную синхронизацию меню
идемпотентной: повторный `PUT /partner/menu` обновляет существующие строки, а не
плодит дубли.

**Таблица идемпотентности** (`idempotency_keys`, уникальный индекс `(client_id, key)`)
— отдельная сущность, а не поле на заказе: ключ должен существовать и быть проверяемым
ещё до того, как заказ вообще создан (в том числе для случая, когда заказ так и не
создался из-за конфликта).

**Пересечение акций запрещено ограничением базы, а не проверкой в коде:**

```sql
EXCLUDE USING gist (
    menu_item_id WITH =,
    tstzrange(starts_at, ends_at) WITH &&
) WHERE (cancelled_at IS NULL)
```

Не может существовать двух неотменённых акций на одну позицию с пересекающимися
временными окнами — требует расширения `btree_gist` (GiST-индексу нужно уметь
одновременно сравнивать `uuid` на равенство и диапазоны на пересечение). Проверка в
коде здесь принципиально не годится: между «проверили — пересечений нет» и «вставили»
проходит время, и два одновременных запроса на создание акции оба пройдут проверку.
База, в отличие от кода, не даст записать конфликт ни при каком стечении обстоятельств.

**Списание остатка — только внутри транзакции оформления заказа**, через
`SELECT ... FOR UPDATE` по строкам `menu_items`, отсортированным по `id` (и, если
среди позиций есть акционные, `rescue_offers` — тем же способом, всегда ПОСЛЕ
блокировки меню). Сортировка — не стиль, а необходимость: без неё два параллельных
заказа, блокирующих одни и те же две строки в противоположном порядке, рано или
поздно образуют классический дедлок (A держит X, ждёт Y; B держит Y, ждёт X).
Фиксированный порядок убирает это в принципе, а не статистически — `TestLockForCheckout_OppositeOrderDoesNotDeadlock`
специально проверяет именно эту гарантию, запуская два запроса с намеренно
противоположным порядком id.

### 7.2. EXPLAIN ANALYZE для трёх ключевых запросов

Индексы под фактические фильтры каталога, не «на всякий случай» — вот что реально
показывает планировщик на демо-данных:

**Фильтр списка заведений по кухне** (использует `venues_cuisine_idx`):
```
Limit  (cost=8.17..8.18 rows=1 width=80) (actual time=0.081..0.081 rows=1 loops=1)
  ->  Sort  (cost=8.17..8.18 rows=1 width=80) (actual time=0.079..0.080 rows=1 loops=1)
        Sort Key: name
        ->  Index Scan using venues_cuisine_idx on venues  (actual time=0.021..0.022 rows=1 loops=1)
              Index Cond: (cuisine = 'Пицца'::text)
Planning Time: 1.380 ms
Execution Time: 0.144 ms
```

**Батч-запрос меню сразу для нескольких заведений** (`WHERE venue_id = ANY($1)` —
именно так список из N заведений получает меню одним запросом, а не N запросами):
```
Seq Scan on menu_items  (cost=0.00..14.68 rows=5 width=72) (actual time=0.010..0.012 rows=11 loops=1)
  Filter: (venue_id = ANY ('{...3 venue ids...}'::uuid[]))
Planning Time: 1.569 ms
Execution Time: 0.030 ms
```
Здесь планировщик честно выбрал `Seq Scan`, а не индекс `menu_items_venue_idx` —
и это правильно: на 11 строках во всей таблице сканировать её целиком дешевле, чем
лезть в индекс. Индекс никуда не делся и включится сам, когда строк станет много —
в этом и смысл `EXPLAIN ANALYZE`, а не «индекс есть — значит, всё в порядке»: план
запроса на демо-данных не обязан совпадать с планом на проде, и врать самому себе
об этом бессмысленно.

**Лента «Спасение остатков»** (частичный индекс `rescue_offers_active_idx`, только
живые непроданные акции):
```
Limit  (cost=8.15..8.19 rows=2 width=24)
  ->  Incremental Sort  (cost=8.15..8.19 rows=2 width=24)
        Sort Key: ends_at, id
        Presorted Key: ends_at
        ->  Index Scan using rescue_offers_active_idx on rescue_offers (actual time=0.008..0.009 rows=0 loops=1)
Planning Time: 1.296 ms
Execution Time: 0.157 ms
```
Индекс покрывает не всю таблицу, а её рабочий срез — воркеру ленты никогда не нужны
отменённые или уже разобранные акции, так что нет смысла держать их в индексе.

## 8. API

Обе спеки — `api/openapi/public.yaml` и `api/openapi/partner.yaml`, OpenAPI 3.0.3,
пишутся до кода: хендлеры реализуют сгенерированный `oapi-codegen`'ом
`StrictServerInterface`, а не наоборот. Открыть и попробовать — Swagger UI на
http://localhost:8081 (раздел 2.3), либо любым другим просмотрщиком спек этих двух
файлов напрямую.

**Публичный контур** (`/api/v1/...`) — для анонимных клиентов. Личность — заголовок
`X-Client-Id`, UUID, который клиент придумывает сам. Ни пароля, ни регистрации, ни
JWT — по допущению (раздел 13), аутентификация пользователей не реализуется.

**Партнёрский контур** (`/api/v1/partner/...`) — для заведений. Заголовок `X-Api-Key`,
статический ключ, выданный заранее демо-сидами; ключ однозначно определяет заведение
(модель «1 партнёр = 1 заведение», раздел 13).

**Это не противоречие с «авторизация не нужна».** Допущение касается
пользовательской аутентификации (пароли, сессии, личный кабинет) — её действительно нет
ни в одном из двух контуров. Партнёрский `X-Api-Key` — это отдельный, независимый
контроль доступа к закрытому списку провайдеров, не имеющий отношения к аутентификации
конечного пользователя.

Общие для обоих контуров правила: версия в пути (`/api/v1`), единый формат ошибки
(`code`/`message`/`details`/`requestId`), курсорная пагинация (`cursor`/`limit` →
`nextCursor`), деньги как `{amountMinor, currency}`, время в RFC 3339 UTC,
`Idempotency-Key` обязателен для `POST /orders`, условные запросы (`ETag`/`If-None-Match`/`304`)
на `GET /venues/{id}/menu`.

## 9. Спасение остатков

Отличительная фишка площадки, не обязательная фича «для галочки».

**Проблема с двух сторон.** У заведения к концу дня остаются готовые блюда и
заготовки, которые назавтра просто спишут в мусор — прямой убыток, а продать по полной
цене уже некому. У площадки часть пользователей отваливается на минимальном чеке:
набрали на 400 при минималке 700 — и ушли, не заказав вообще ничего.

**Решение.** Заведение выставляет акцию на конкретную позицию: скидка в процентах,
ограниченное количество, временное окно. Площадка показывает такие позиции отдельной
подборкой (`GET /rescue`), отсортированной по времени до закрытия окна, и применяет
цену акции автоматически при оформлении. Заведение возвращает хотя бы часть
себестоимости вместо нуля; пользователь получает скидку и заодно способ добрать до
минимального чека дешевле, чем ещё одной позицией по полной цене.

**Оффер — самостоятельная сущность** (`rescue_offers`), а не поле на позиции меню. У
него своё окно, своё количество и свой остаток, независимый от `menu_items.stock_qty`
— у одной позиции сегодня акция есть, завтра нет, и общий остаток эту акцию не
ограничивает: заведение решает, сколько из имеющегося отдать со скидкой, а не «всё,
что осталось».

**Активность акции вычисляется при чтении, а не хранится.** Никакого фонового процесса,
который «включает» и «выключает» акции по расписанию, в системе нет — активность это
чистая функция от `starts_at`/`ends_at`/`remaining_quantity`/`cancelled_at` и текущего
времени. Хранить производное состояние, которое можно однозначно вычислить из уже
имеющихся данных, значит завести источник рассинхронизации: рано или поздно фоновый
процесс отстанет от реальности, и придётся отдельно чинить именно это.

**Пересечение окон запрещено на уровне базы** (`EXCLUDE USING gist`, раздел 7) — не
проверкой в коде, ровно по той же причине, по которой это работает для любой другой
гонки в этом проекте: между «проверил» и «записал» проходит время, и только сама база
может гарантировать, что два одновременных запроса не создадут два конфликтующих
оффера одновременно.

**Если акции не хватает на весь запрошенный объём — заказ не отклоняется, а делится.**
Запросили 5, осталось по акции 3 — в заказе появляются две строки: 3 по цене акции,
2 по полной. Это единственная внутренняя неоднозначность плана (раздел 5.5 описывает
деление как обычный успешный сценарий, а таблица конфликтов раздела 5.2 называет ту же
ситуацию `PRICE_CHANGED`) — решение зафиксировано в пользу раздела 5.5, буквально по
формулировке теста «деление строки». `RESCUE_OFFER_EXPIRED` оставлен
только за случаем, когда закрылось само окно оффера целиком (истекло время или акцию
отменили), а не когда просто кончилось акционное количество.

**Списание акционного остатка** происходит в той же транзакции оформления заказа, что
и списание обычного остатка, теми же правилами блокировки и тем же порядком по `id` —
`rescue_offers` блокируется строго после `menu_items`, чтобы фиксированный порядок
блокировок не давал двум параллельным заказам, пересекающимся сразу по позиции и по
акции на неё, образовать взаимную блокировку.

**Цена со скидкой** — `floor(price_minor * (100 - discount_percent) / 100)`, округление
вниз, в пользу пользователя.

## 10. Ключевые технические решения

**Идемпотентность.** `Idempotency-Key` обязателен для `POST /orders`. Ключ и хэш тела
запроса запоминаются отдельной таблицей ещё до попытки создать заказ (`Claim`), потом
после успешного создания привязываются к получившемуся заказу (`LinkOrder`) — так
разнесено специально: если между этими двумя шагами процесс упадёт, повторный запрос
с тем же ключом увидит «клейм есть, заказа ещё нет» и корректно попробует снова, а не
получит вечно висящий недооформленный заказ. Тот же ключ с другим телом запроса —
`IDEMPOTENCY_KEY_CONFLICT`: это ошибка на стороне клиента (переиспользовал ключ для
другого запроса), а не то же самое, что успешный повтор.

**Защита от гонок при списании остатков.** `SELECT ... FOR UPDATE` по `menu_items`
(и, если нужно, `rescue_offers`), обязательно отсортированным по `id` перед
блокировкой — раздел 7 разбирает, почему сортировка обязательна, а не только
`FOR UPDATE`.

**Outbox.** Заказ и событие о нём пишутся одной транзакцией (раздел 11 — почему это
вообще нужно, независимо от брокера). Фоновый воркер вычитывает `outbox_events` через
`SELECT ... FOR UPDATE SKIP LOCKED`, атомарно захватывая свою партию сдвигом
`next_attempt_at` вперёд на короткую «аренду» — так несколько экземпляров воркера
могут поллить одну таблицу без риска доставить одно событие дважды даже при падении
процесса посреди отправки.

**Вебхук плюс поллинг одновременно, не «или-или».** Заведение получает уведомление о
заказе вебхуком (быстро) и одновременно может опросить `GET /partner/orders`
(надёжно). Вебхук — at-least-once с пятью попытками нарастающей паузы (30с/2м/10м/30м),
после которых событие помечается `failed` и не ретраится дальше — но заказ при этом не
теряется: он всё ещё виден поллингом. Обе гарантии дешёвые по отдельности и вместе
покрывают друг друга: то, что не долетело вебхуком, найдётся поллингом, а поллинг не
нужно дёргать поминутно, если вебхуки обычно доходят.

**Стейт-машина.** Явная таблица допустимых переходов (`internal/domain/order/status.go`),
а не цепочка `if`/`switch`, разбросанная по коду. Вся логика лежит в одном месте
и видна целиком; недопустимый переход — не забытая ветка, а осознанный отказ
`ORDER_INVALID_STATE_TRANSITION`. Каждый переход пишется в `order_status_history`
(откуда, куда, кто инициировал, когда) — это то, что делает возможным честный разбор
спорных заказов.

## 11. События и брокер сообщений

Брокер сообщений (Kafka и подобные) в проекте **не используется**. Тезис, который
важно уметь объяснить: **готовность к масштабированию обеспечивают outbox, строгий
контракт события и публикация за интерфейсом — а сам брокер это уже само
масштабирование, которое пока не требуется.**

**Outbox нужен независимо от брокера** — он решает проблему двойной записи: нельзя
одной транзакцией и изменить базу, и отправить сообщение наружу (транзакция может
откатиться уже после того, как запрос ушёл). Брокер эту проблему не решает — записать
в PostgreSQL и одновременно опубликовать в Kafka одной транзакцией так же нельзя, как
и с прямым HTTP-вызовом. С брокером цепочка становится
`транзакция → outbox → воркер → брокер → потребитель`, то есть добавляется звено, а
не убирается. Поэтому дёшево заменяется только последнее звено — доставка, — и эта
дешевизна не бесплатна сама по себе, её нужно готовить заранее тремя вещами, и все
три уже сделаны:

1. **Событие — строгий контракт** (`event_id`, `event_type`, `event_version`,
   `occurred_at`, `aggregate_type`, `aggregate_id`, `payload`), а не произвольный
   JSON. Это единственная часть, которую дорого менять задним числом — формат
   пришлось бы согласовывать с уже подключёнными внешними потребителями.
2. **Публикация спрятана за интерфейсом** `EventPublisher.Publish(ctx, event) error`.
   Сейчас единственная реализация — `webhook.Publisher`. `KafkaPublisher` будет новым
   файлом, реализующим тот же интерфейс, а не правками по всему коду, которое его
   вызывает.
3. **Ключ партиционирования выбран заранее** — это `aggregate_id`, то есть `order_id`.
   Обоснование: брокер гарантирует порядок сообщений только внутри одной партиции;
   если `order.created` и `order.cancelled` одного заказа разъедутся по разным
   партициям, потребитель рискует увидеть отмену раньше создания. Реализовывать
   сейчас нечего — Kafka не поднята, — но решение принято и не потребует
   пересмотра, когда брокер появится.

Потребители обязаны быть идемпотентны по `event_id` — это уже часть контракта
вебхуков (`X-Event-Id`), так что переход на доставку «хотя бы один раз» через брокер
ничего не сломает задним числом.

Поставить Kafka сейчас означало бы не готовность к масштабированию, а само
масштабирование — при одном получателе (`venue-pasta-roma`) и текущем профиле
нагрузки таблица в PostgreSQL полностью справляется, а брокер добавил бы
инфраструктуру, за которую прямо сейчас некому заплатить выигрышем. Второй
потребитель событий появляется только на целевой микросервисной схеме (раздел 5) — и
именно тогда брокер оправдан.

## 12. Кэширование

Кэш (Redis, кэш в памяти) в проекте **не используется** — по той же причине, что и
брокер: оптимизировать без замеров нельзя, а замеров, показывающих реальную проблему,
пока нет. Но швы под будущий кэш подготовлены, а базовые вещи, которые не оптимизация,
а условие адекватности кода, сделаны сразу.

**Что сделано сейчас:**
- Индексы под фактические фильтры каталога, проверенные `EXPLAIN ANALYZE` (раздел 7.2),
  а не «на всякий случай».
- Ноль N+1: список заведений не порождает по отдельному запросу на меню каждого —
  один `WHERE venue_id = ANY($1)`.
- Курсорная пагинация вместо `OFFSET`.
- `venues.menu_version` — счётчик, растущий на 1 в той же транзакции, что меняет
  меню, категории, цены, стоп-лист, остатки или акции. На нём построен `ETag`:
  `GET /venues/{id}/menu` отдаёт `ETag` вида `"{venueId}-{menuVersion}"`, и повторный
  запрос с тем же `If-None-Match` получает `304 Not Modified` без тела — вместо
  пересборки всего меню это одна выборка по первичному ключу.

**Лестница решений, если нагрузка когда-нибудь это оправдает:**

- **Ступень 1 — кэш в памяти процесса.** Первый шаг, ловушка — cache stampede: когда
  запись протухает и разом прилетает сотня запросов, все идут в базу за одним и тем
  же — база получает удар именно тогда, когда её должны были разгрузить. Лечится
  `golang.org/x/sync/singleflight`.
- **Ступень 2 — Redis.** Нужен не потому что «кэш в памяти медленный», а когда
  появляется несколько экземпляров приложения (кэш в памяти каждого своя, не общая),
  когда кэш должен пережить перезапуск процесса, либо когда нужны атомарные счётчики
  или распределённые блокировки. Redis решает проблему **общего** кэша, а не
  **быстрого** — это разные задачи, и путать их значит выбрать Redis не по той причине.
- **Ступень 3** — реплика для чтения, отдельная денормализованная модель чтения.

**Что кэшировать нельзя категорически: доступность, стоп-лист, остатки, активность
акций.** Закэшированная доступность означает продажу того, чего физически уже нет.
Формально систему спасёт жёсткая проверка внутри транзакции оформления — заказ
корректно не создастся, — но пользователь получит отказ уже после того, как собрал
корзину и ввёл адрес доставки, то есть в худший из возможных моментов. Ответ с меню
собирается из двух источников уже сейчас: структура (в будущем — кэшируемая часть) и
актуальная доступность (всегда свежий запрос) — это и есть тот самый подготовленный
шов, а не то, что придётся переписывать при добавлении кэша.

**Инвалидация уже есть, изобретать новый канал не придётся** — при любом изменении
меню событие и так пишется в outbox; тот же воркер сможет сбрасывать кэш по этому же
каналу. У акций «спасение» есть `ends_at` — точное время, когда ответ гарантированно
устареет, значит время жизни кэша для них можно ставить не наугад, а точно до конца
ближайшего окна.

## 13. Допущения и упрощения

Полная и честная таблица упрощений ведётся в [`docs/schema-decisions.md`](docs/schema-decisions.md)
(там же — обоснование каждого решения по схеме БД); ключевые пункты:

| Упрощение | Почему |
|---|---|
| Расписание не поддерживает смены через полночь | Усложняет проверку «открыто ли сейчас», не влияет на основную логику |
| Одна валюта, поле `currency` в запросах не заводится | Мультивалютность вне scope; в ответах поле оставлено ради формата и будущего расширения |
| Телефон и адрес — свободный текст, без валидации формата и геокодирования | Зона доставки — необязательный сценарий |
| Корзина живёт вечно, TTL не чистится | Для MVP не критично; при росте — фоновая уборка по `updated_at` одной командой |
| Скидка по акции только в процентах, одна акция на позицию одновременно | Фиксированная сумма и наложение скидок — отдельные продуктовые задачи |
| Модель доступа «1 партнёр = 1 заведение» | `X-Api-Key` однозначно определяет заведение — при партнёре с несколькими заведениями это было бы неоднозначно без лишнего поля в схеме |
| `venue-pasta-roma` продвигает статусы каждые несколько секунд, а не за реалистичные минуты приготовления | Длительность нигде не зафиксирована; секунды выбраны, чтобы в демо был виден полный цикл, не дожидаясь реального времени |
| Состояние `venue-pasta-roma` — только в памяти, теряется при перезапуске | Не упрощение, а осознанное архитектурное решение (раздел 8.1 плана) |
| Outbox-воркер — горутина внутри процесса `api`, а не отдельный сервис | Один процесс проще эксплуатировать на масштабе MVP; вынесение в отдельный воркер — чисто операционное изменение (другой `cmd/`, тот же код), не архитектурное |
| Неудачный `AcceptOrder`/`RejectOrder` у `venue-pasta-roma` ретраится без ограничения попыток, в отличие от исходящего вебхука платформы | Получатель здесь — сама платформа, предмет этого задания, а не произвольная третья сторона; `409` на повторе считается успехом (более ранняя попытка на самом деле дошла) |
| Дедупликация входящих вебхуков ограничена последними 10000 событий (вытеснение по очереди) | Простая защита от неограниченного роста памяти за время жизни процесса |

## 14. Точки роста

**Складчина.** Соседи по дому скидываются на один заказ, чтобы вместе перешагнуть
минимальный чек. Пул открыт ограниченное время; позиции участников удерживаются мягким
резервом со сроком жизни; при истечении окна резервы освобождаются, и пул распадается
сам. Заведение получает один заказ вместо нескольких мелких, курьер едет один раз.
Технически это вторая стейт-машина, переходы в которой идут по таймеру и по
достижению суммы, а не по команде человека — тот же приём, что уже есть у заказа
(раздел 5.4), только источник переходов другой.

**Автоматические правила акций.** Включать скидку за N часов до закрытия заведения
самостоятельно, без ручного создания оффера партнёром — сейчас это целиком ручное
действие (раздел 5.5, упрощения).

**Вынос поиска в отдельный движок** — полнотекстовый поиск по названиям и составу
блюд, если `LIKE`/`ILIKE` перестанет справляться по производительности или полноте.

**Шардирование заказов** — если объём заказов на одну базу PostgreSQL станет узким
местом; естественный ключ шардирования здесь тот же, что и ключ партиционирования
будущего брокера — `order_id`/`venue_id`.

## 15. Разработка

```bash
make build              # go build обоих модулей (основной сервис + venue-pasta-roma)
make test                # юнит-тесты
make test-integration    # интеграционные — поднимают реальный Postgres в Docker (testcontainers-go)
```

`make generate` нужно перезапускать после правки любого `api/openapi/*.yaml` или
любого `ports.go` — `internal/generated/**` и каждый `mock_test.go` целиком машинные,
руками не редактируются. CI (`.github/workflows/ci.yml`) проверяет это отдельным
шагом: гоняет `make generate` и падает, если появился `git diff`.

**Интеграционные тесты на Windows.** Тесты поднимают Postgres через testcontainers.
Вместе с ним библиотека запускает служебный контейнер Ryuk, который удаляет тестовые
контейнеры после прогона. С Docker Desktop на Windows он иногда не стартует, и тесты
падают ещё до запуска. Тогда отключите его:

​```powershell
$env:TESTCONTAINERS_RYUK_DISABLED = "true"   # PowerShell
​```
​```bash
export TESTCONTAINERS_RYUK_DISABLED=true     # Git Bash / Linux / macOS
​```

Тестовые контейнеры в этом случае после прогона остаются, их можно убрать вручную
через `docker rm -f`.

`cmd`/PowerShell, ни в Git Bash — эквивалентные команды прямым текстом, копируются
