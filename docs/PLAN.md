## 0. Роль и режим работы

Реализуешь pet-проект — MVP платформы доставки еды, в идиоматичном,
продакшен-готовом стиле на Go.

Правила работы:

1. **Идёшь по этапам из раздела 13.** После каждого этапа останавливаешься, показываешь
   результат и ждёшь подтверждения. Не пытайся сделать всё за один заход.
2. **Объясняй, что делаешь.** Автор — начинающий разработчик, который должен понимать
   и уметь объяснить каждую строку. Перед каждым нетривиальным куском кода коротко
   объясни: какую задачу он решает, какие были альтернативы и почему выбран этот вариант.
   Если в коде появляется приём, которого не было раньше в проекте, добавь пояснение.
3. **Не используй библиотеки вне списка в разделе 4.** Нужна ещё одна — сначала предложи
   и обоснуй.
4. **Не пиши код «на вырост».** Каждая абстракция оправдана текущим требованием.
5. **Все допущения и упрощения записывай в README.** Упрощать можно, но каждое
   упрощение нужно обосновать.
6. **Код, комментарии, названия, тексты ошибок, коммиты — на английском.**
   README и диаграммы — на русском.
7. При конфликте требований — остановись и спроси.

## 1. Глоссарий

Термины, которые встречаются дальше по тексту. Все они должны быть понятны автору решения.

| Термин | Что это |
|---|---|
| **Модульный монолит** | Одно приложение и одна база, но код разделён на модули с жёсткими границами. Модули общаются только через объявленные интерфейсы, поэтому любой можно потом вынести в отдельный сервис |
| **Порт / адаптер** | Порт — интерфейс, объявленный бизнес-логикой («сохрани заказ»). Адаптер — конкретная реализация порта (репозиторий на PostgreSQL). Бизнес-логика не знает, что под ней база |
| **Транзакция** | Группа операций с БД: применяются либо все, либо ни одной |
| **Гонка (race condition)** | Два одновременных запроса читают одно и то же состояние и оба принимают решение на устаревших данных. Классика: два заказа на последнюю единицу товара |
| **`SELECT ... FOR UPDATE`** | Блокировка строки внутри транзакции. Второй запрос ждёт, пока первый завершится. Лечит гонку |
| **Идемпотентность** | Повтор одного и того же запроса не создаёт дубль, а возвращает прежний результат |
| **Outbox** | Таблица «исходящих сообщений». Внутри транзакции нельзя слать HTTP: транзакция может откатиться, а запрос уже ушёл. Поэтому пишем событие в таблицу той же транзакцией, а фоновый воркер потом его отправляет |
| **Вебхук** | Внешняя система сама шлёт нам HTTP-запрос, когда что-то произошло. Обратное поллингу |
| **Поллинг** | Мы сами периодически спрашиваем «есть новое?» |
| **At-least-once** | Гарантия «доставим хотя бы раз, возможно, несколько». Поэтому получатель обязан быть идемпотентным |
| **Стейт-машина** | Явная таблица допустимых переходов между статусами вместо россыпи `if` |
| **HMAC-подпись** | Хеш от тела запроса и общего секрета в заголовке. Получатель считает такой же и сверяет: так он убеждается, что запрос действительно от нас |
| **Миграции** | Пронумерованные SQL-файлы, пошагово создающие и меняющие схему БД. Применяются автоматически, откатываются |
| **OpenAPI** | Формат описания HTTP-API в YAML. По нему можно сгенерировать серверные интерфейсы и клиентов |
| **Кодогенерация** | Сервер и клиент генерируются из OpenAPI-файла, а не пишутся руками. Спека становится источником правды |
| **Линтер** | Программа, проверяющая код на ошибки и нарушения стиля до запуска |
| **CJM** | Customer Journey Map — карта пути пользователя по шагам с указанием, где он спотыкается |
| **C4** | Нотация для схем архитектуры: уровень 1 — система и её окружение, 2 — из каких запускаемых частей состоит, 3 — что внутри одной части |
| **ERD** | Схема таблиц базы и связей между ними |
| **testcontainers** | Библиотека, поднимающая настоящий PostgreSQL в Docker на время теста. Тест работает с реальной базой, а не с заглушкой |

## 2. Контекст и цель

MVP сервиса доставки еды: заведения (рестораны, кафе, магазины) размещают меню,
пользователи оформляют заказы на доставку.

Главный фокус — **подход к проектированию**, а не количество фич. Приоритеты по убыванию:

1. Границы модулей и контракты — систему должно быть реально масштабировать после MVP.
2. Честная обработка конфликтов: остатки, стоп-лист, расписание, повторные запросы.
3. Документация: README, C4, CJM, ERD, OpenAPI.
4. Полнота функционала.

Требования, которые нельзя потерять:

- Всё в одном репозитории.
- Два API: для заведений (закрытый доступ) и для клиентской части.
- Отдельный сервис-заведение, поднимается в том же Docker Compose, ходит в API основного
  сервиса и предоставляет свой.
- Миграции со схемами БД, спецификации OpenAPI.
- CJM с обеих сторон, диаграммами, генерируемыми из кода (PlantUML).
- README: описание проекта, архитектура (C4 уровня 2–3), описание схемы БД.
- Настроенный линтер, конфиг лежит в репозитории.
- Приложение поднимается и реализует все заявленные сценарии.

Зафиксировать эти решения и продублировать в README.

| Место в ТЗ | Как трактуем |
|---|---|
| «Авторизацию и аутентификацию пользователей реализовывать не нужно» | Клиент анонимен. Корзина и заказы привязываются к `X-Client-Id` (UUID, который клиент генерирует сам и шлёт в заголовке). Ни паролей, ни регистрации, ни JWT |
| «Закрытый доступ к списку провайдеров» | Партнёрский API закрыт статическими API-ключами, выданными заранее (создаются сидами). Заголовок `X-Api-Key`. Это не пользовательская авторизация, так что противоречия с пунктом выше нет |
| «Наличие товара в стакане» | Опечатка, читается как «в стоке». Делаем два независимых механизма: стоп-лист (позицию выключили вручную) и остаток (кончилось количество) |
| «Для зарубежных направлений... пример одного заведения» | Речь о внешней интеграции: отдельный сервис, изображающий собственную систему заведения |
| «Как связать данные в системе с источниками данных и пользователями» | Всё, что пришло извне, хранит `source` (`platform` или `integration`) и `external_id`. Заказы, ушедшие во внешнюю систему, хранят `external_order_id`. Клиент связывается через `client_id` |
| «Подсоединения для английского языка» (в разделе про линтеры) | Проверка английской орфографии в коде: линтер `misspell` с `locale: US` |

## 4. Стек

Всё на Go. Python и другие языки не использовать.

**Основной сервис (Go 1.23+):**

- Роутер: `go-chi/chi/v5`
- Генерация из OpenAPI: `oapi-codegen` (режим `std-http-server` или `chi-server`, strict-режим)
- БД: PostgreSQL 16, драйвер `jackc/pgx/v5` + `pgxpool`
- Миграции: `pressly/goose/v3`, SQL-файлы, вшитые через `//go:embed`
- Конфиг: `caarlos0/env/v11`, только переменные окружения
- Логи: стандартный `log/slog`, JSON, с `request_id`
- Тесты: стандартный `testing` + `stretchr/testify`, интеграционные — `testcontainers-go`
- Моки: `go.uber.org/mock`
- Линтер: `golangci-lint` v1.62+
- UUID: `google/uuid`
- Деньги: хранить целым числом копеек (`int64`). Никаких `float`

**Сервис-заведение — тоже Go** (см. раздел 8).

**Инфраструктура:** Docker (multi-stage сборка), Docker Compose, Makefile,
PlantUML (рендер через контейнер `plantuml/plantuml`), GitHub Actions.

Не использовать: ORM (GORM и подобные), DI-контейнеры на рефлексии, глобальные синглтоны,
`panic` для обработки ожидаемых ошибок.

### 5.2. Клиент, конфликтные сценарии

Это **самая важная часть задания** — ТЗ прямо просит проанализировать, с какими трудностями
сталкивается пользователь. Каждый случай возвращает свой код ошибки.

| Ситуация | Код | HTTP | Что в ответе |
|---|---|---|---|
| Заведение закрыто по расписанию | `VENUE_CLOSED` | 409 | Время следующего открытия |
| Заведение временно не принимает заказы | `VENUE_NOT_ACCEPTING_ORDERS` | 409 | — |
| Позиция ушла в стоп-лист, пока лежала в корзине | `ITEM_UNAVAILABLE` | 409 | Список конкретных позиций |
| Остатка не хватает | `INSUFFICIENT_STOCK` | 409 | Сколько доступно по каждой позиции |
| Цена изменилась после добавления в корзину | `PRICE_CHANGED` | 409 | Старая и новая цена |
| Сумма меньше минимального чека | `MIN_ORDER_AMOUNT_NOT_REACHED` | 422 | Сколько не хватает |
| Повторный запрос с тем же `Idempotency-Key` | — | 200 | Тот же заказ, дубль не создаётся |
| Тот же ключ, но другое тело запроса | `IDEMPOTENCY_KEY_CONFLICT` | 409 | — |
| Акция «спасение» закончилась, пока позиция лежала в корзине | `RESCUE_OFFER_EXPIRED` | 409 | Новая цена и время окончания акции |
| По акции разобрали часть количества, итог вырос | `PRICE_CHANGED` | 409 | Разбивка: сколько по цене акции, сколько по полной |
| **[если останется время]** Адрес вне зоны доставки | `DELIVERY_ADDRESS_OUT_OF_ZONE` | 422 | — |

**Важное правило:** доступность проверяется дважды. «Мягко» при добавлении в корзину —
чтобы сразу показать пользователю проблему. «Жёстко» внутри транзакции оформления заказа —
чтобы данные остались консистентными. В README объяснить, почему первой проверки мало:
между добавлением в корзину и оформлением проходит время, за которое товар может кончиться.

### 5.4. Стейт-машина заказа

```
                    ┌─→ rejected        (заведение отклонило, с причиной)
created ─→ confirmed ─→ cooking ─→ ready ─→ delivering ─→ delivered
    │          │
    └──────────┴─→ cancelled            (клиент отменил, только до cooking)
```

Реализовать явной таблицей допустимых переходов в доменном слое, а не цепочкой `if`.
Недопустимый переход → `ORDER_INVALID_STATE_TRANSITION` (409). Каждый переход пишется
в `order_status_history`: откуда, куда, кто инициировал, когда.

### 5.5. Спасение остатков — отличительная особенность площадки

**Проблема.** К концу дня у заведения остаются готовые блюда и заготовки, которые завтра
пойдут в мусор. Списать их — прямой убыток. Продать по полной цене поздно, желающих уже нет.
Одновременно часть пользователей отваливается на минимальной сумме заказа: набрали на 400
при минималке в 700 и ушли.

**Решение.** Заведение выставляет акцию на конкретные позиции: скидка, количество и временное
окно (например, с 20:00 до 23:00, 5 порций, минус 40%). Площадка показывает такие позиции
отдельной подборкой, отсортированной по времени до закрытия окна, и применяет цену акции
автоматически при оформлении заказа.

Заведение возвращает хотя бы часть себестоимости вместо списания в ноль и получает заказы
от людей, которые при полной цене не пришли бы. Пользователь получает дешевле. Площадка
получает конверсию там, где сейчас отказ.

#### Правила

**Оффер — самостоятельная сущность,** а не поле у позиции меню. У него своё окно, своё
количество и свой остаток. У одной позиции сегодня акция есть, завтра нет.

**Количество по акции считается отдельно от общего остатка.** У заведения может быть
8 порций, из которых по скидке отдаётся только 3. Заказ на 5 порций делится: 3 по цене
акции, 2 по полной, в заказе это две отдельные строки. Итог пересчитывается, разбивка
возвращается клиенту.

**Цена со скидкой** считается как `floor(price_minor * (100 - discount_percent) / 100)`.
Округление вниз, в пользу пользователя. Правило зафиксировать в README, потому что округление
денег — классический источник расхождений на копейку.

**Активность оффера вычисляется при чтении**, от текущего времени. Никакого фонового процесса,
который «включает» и «выключает» акции, заводить не нужно. Это отдельное решение, объяснить
его в README: состояние, однозначно выводимое из данных и времени, не надо хранить и
синхронизировать.

Оффер считается активным, когда выполнено всё сразу:

| Условие | Если не выполнено |
|---|---|
| Текущее время внутри `[starts_at, ends_at)` | Оффер не показывается, позиция продаётся по полной цене |
| `remaining_quantity > 0` | Оффер разобран, позиция продаётся по полной цене |
| Позиция не в стоп-листе и `stock_qty` позволяет | Позиция недоступна целиком, вместе с акцией |
| Заведение открыто и принимает заказы | Подборка не показывает позиции закрытых заведений |

**Списание остатка по акции** происходит в той же транзакции, что и списание обычного
остатка, теми же правилами блокировки и сортировки по `id`. То есть заказ уменьшает и
`menu_items.stock_qty`, и `rescue_offers.remaining_quantity`.

**Сумма по акции засчитывается в минимальный чек** по фактической, сниженной цене.

**Пересечение акций запрещено на уровне базы.** Для одной позиции не может существовать двух
офферов с пересекающимися окнами. Реализуется exclusion constraint (см. раздел 9), а не
проверкой в коде: база не даст записать конфликт даже при гонке двух параллельных запросов.

#### Ошибки партнёрского API

| Ситуация | Код | HTTP |
|---|---|---|
| Окно пересекается с уже существующей акцией на эту позицию | `RESCUE_OFFER_OVERLAP` | 409 |
| `ends_at` не позже `starts_at`, или окно целиком в прошлом | `RESCUE_INVALID_WINDOW` | 422 |
| Скидка вне диапазона 1–90 процентов | `RESCUE_INVALID_DISCOUNT` | 422 |

#### Что обязательно покрыть тестами

- Расчёт цены со скидкой и округление, включая нечётные суммы.
- Деление строки заказа, когда запрошено больше, чем осталось по акции.
- Оффер, истёкший между добавлением в корзину и оформлением заказа.
- Два параллельных заказа на последнюю единицу по акции.
- Попытка создать пересекающийся оффер.

#### Упрощения для MVP (записать в README)

- Скидка задаётся только в процентах, фиксированной суммы нет.
- Одна акция на позицию в один момент времени.
- Нет автоматических правил вроде «включать скидку за два часа до закрытия» — заведение
  создаёт акции вручную.
- Нет ограничения «не более N акционных позиций в одни руки».

## 6. Архитектура

### 6.1. Выбранный стиль и обоснование

**Модульный монолит:** одно приложение, одна база, но код разрезан на модули с жёсткими
границами.

Модули:

- `catalog` — заведения, меню, доступность, расписание
- `order` — корзина, заказы, стейт-машина
- `partner` — партнёры и их API-ключи
- `integration` — outbox и доставка вебхуков

Обоснование для README (сформулировать своими словами, это будут спрашивать на собеседовании):

> ТЗ требует готовности к масштабированию, а не распределённости самой по себе. Основная
> техническая сложность домена — атомарное списание остатков при оформлении заказа.
> В монолите это одна транзакция с блокировкой строк: коротко и невозможно ошибиться.
> Если разнести каталог и заказы по разным сервисам с разными базами, эта транзакция
> исчезает, и её приходится заменять сагой: резервирование остатков с таймаутом, отдельный
> воркер освобождения зависших резервов, компенсирующие операции на каждый сбой, отдельный
> outbox в каждом сервисе, контрактные тесты и сквозной трейсинг. Это примерно вдвое
> больше кода, и почти весь прирост — инфраструктурный, а не доменный.
>
> При этом настоящие распределённые задачи в проекте всё равно решаются: интеграция
> с внешним сервисом-заведением — это отдельный процесс, общающийся по контракту, с
> гарантией at-least-once, идемпотентностью на приёме, ретраями и компенсацией при
> отклонении заказа.
>
> Границы модулей проверяются линтером, а не обещанием: `depguard` запрещает модулям
> импортировать внутренности друг друга. Порядок отделения в микросервисы, если он
> понадобится, описан в разделе «Микросервисный вариант».

### 6.2. Правила зависимостей

Проверяются линтером `depguard`, а не на словах:

- `domain` не импортирует ничего, кроме стандартной библиотеки и `uuid`. Никакого SQL,
  HTTP, логгера.
- `usecase` зависит от `domain` и от **интерфейсов-портов**, которые объявляет сам.
- `adapter/*` зависит от `usecase` и `domain` и реализует порты. Адаптеры не знают друг о друге.
- Модули общаются между собой только через публичный пакет `<module>/api`. Импорт чужого
  `internal` запрещён.
- Зависимости всегда направлены внутрь. Циклы запрещены.

### 6.5. Контракт события и подготовка к брокеру

Брокер сообщений (Kafka и подобные) в проекте **не используется**. Но outbox проектируется
так, чтобы переход на брокер был заменой одного компонента, а не переделкой системы.

Ключевая мысль, которую надо усвоить и уметь объяснить: **outbox нужен независимо от
брокера**. Он решает проблему двойной записи — невозможность атомарно изменить базу
и отправить сообщение наружу. Брокер эту проблему не решает: записать в PostgreSQL
и опубликовать в Kafka одной транзакцией тоже нельзя. С брокером схема становится
`транзакция → outbox → воркер → брокер → потребитель`, то есть добавляется звено, а не
убирается.

Поэтому дёшево меняется только последний шаг. Чтобы он действительно менялся дёшево,
нужны три вещи, и все три делаются сейчас.

**Первое: событие — строгий контракт, а не произвольный JSON.** Это единственная часть,
которую дорого менять задним числом, потому что формат придётся согласовывать с внешними
потребителями. Формат фиксируем сразу:

```json
{
  "event_id": "01J8X...",
  "event_type": "order.created",
  "event_version": 1,
  "occurred_at": "2026-08-29T12:00:00Z",
  "aggregate_type": "order",
  "aggregate_id": "9f2c...",
  "payload": { }
}
```

- `event_id` — для дедупликации на приёме. Уходит в заголовок `X-Event-Id`.
- `event_version` — позволит менять формат, не ломая старых потребителей.
- `aggregate_id` — будущий ключ партиционирования.
- `occurred_at` — время бизнес-события, не время отправки.

**Второе: публикация спрятана за интерфейсом.** Воркер не знает, куда отправляет:

```go
type EventPublisher interface {
    Publish(ctx context.Context, e Event) error
}
```

Сейчас реализация одна — `WebhookPublisher`. Добавление `KafkaPublisher` будет новым файлом,
а не правками по всему коду.

**Третье: ключ партиционирования выбран и обоснован заранее.** Это `aggregate_id`, то есть
`order_id`. Обоснование: брокер гарантирует порядок сообщений только внутри одной партиции.
Если события одного заказа разъедутся по разным партициям, `order.confirmed` может прийти
раньше `order.created`. Реализовывать сейчас нечего, но решение принято и записано в README.

Плюс потребители обязаны быть идемпотентными по `event_id` — у нас это уже часть контракта
вебхуков, так что переход на доставку «хотя бы один раз» ничего не сломает.

Формулировка для README (изложить своими словами):

> Готовность к масштабированию обеспечивается транзакционным outbox, строгим контрактом
> события и публикацией за интерфейсом. Сам брокер — это последняя миля, и добавляется
> она тогда, когда появляется второй потребитель. Поставить Kafka заранее означало бы
> не готовность к масштабированию, а само масштабирование, которое пока не требуется:
> при одном получателе и текущем профиле нагрузки таблица в PostgreSQL справляется,
> а брокер добавил бы инфраструктуру без выигрыша.

### 6.6. Производительность каталога и кэширование

Кэш в проекте **не используется**: ни Redis, ни кэш в памяти. Причина та же, что с брокером —
оптимизировать без замеров нельзя, а замеров, показывающих проблему, у нас нет. Но шов
для будущего кэша подготавливается, а базовые вещи делаются сразу.

#### Что делается сейчас, обязательно

**Нормальные запросы.** Это не оптимизация, это условие адекватности кода:

- Индексы под фактические фильтры каталога (`cuisine`, `is_open`, поиск по названию).
  Проверять через `EXPLAIN ANALYZE`, а не на глаз.
- **Никаких N+1.** Список из 20 заведений не должен порождать 20 отдельных запросов за меню.
  Только один запрос с `JOIN` или `WHERE venue_id = ANY($1)`.
- Курсорная пагинация вместо `OFFSET` (уже заложена в разделе 7.1).

**Колонка `menu_version`** на `venues` — целочисленный счётчик, увеличивающийся на единицу
при любом изменении меню, категорий, цен, стоп-листа или акций. Стоит одну строку в миграции
и одно `UPDATE` в транзакции изменения. Открывает и `ETag`, и будущую инвалидацию кэша.

**Условные запросы через `ETag` и `304`.** На `GET /api/v1/venues/{venueId}/menu` отдаём
заголовок `ETag` со значением, собранным из `venue_id` и `menu_version`. Если клиент присылает
`If-None-Match` с тем же значением — отвечаем `304 Not Modified` без тела. Проверка стоит один
запрос по первичному ключу вместо сборки всего меню. Ноль новых зависимостей, ноль контейнеров.

**Разделение медленной и быстрой частей меню в коде.** Это ключевое правило домена, и оно
важнее самого кэша:

| Часть | Что входит | Как часто меняется | Кэшируема |
|---|---|---|---|
| Медленная | Названия, описания, категории, цены, состав | Дни и недели | Да |
| Быстрая | Стоп-лист, `stock_qty`, `accepting_orders`, активность акции | Минуты | **Категорически нет** |

Ответ с меню собирается из двух источников: структура (в будущем — из кэша) плюс актуальное
состояние доступности (всегда свежим запросом, это выборка нескольких колонок по индексу).

Причина запрета: закэшированная доступность означает продажу того, чего нет. Формально нас
спасёт жёсткая проверка в транзакции оформления, и заказ не создастся. Но пользователь получит
отказ уже после того, как собрал корзину и ввёл адрес — то есть в худший возможный момент.

Собирать ответ надо так, чтобы будущий кэш вставлялся в готовое место, а не требовал
переписывать сборку. Тот же приём, что с `EventPublisher`: подготовить шов, не строя
конструкцию.

#### Что НЕ делается сейчас

Redis, кэш в памяти, реплики для чтения, отдельная модель чтения. Всё это описывается
в README как лестница решений с указанием, что на какой ступени и при каких условиях
включается (см. 12.4).

Отдельно зафиксировать в README две вещи, которые понадобятся при внедрении кэша:

- **Инвалидация уже есть.** При изменении меню событие и так пишется в outbox. Тот же
  воркер сможет сбрасывать кэш — отдельный канал изобретать не придётся.
- **Cache stampede.** Когда запись протухает и одновременно прилетает сотня запросов, все
  они идут в базу за одним и тем же, и база получает удар ровно тогда, когда её должны были
  разгрузить. Лечится `golang.org/x/sync/singleflight`. Упомянуть как известную ловушку.
- **У акций «спасение» есть `ends_at`** — точное время, когда ответ гарантированно устареет.
  Это позволяет ставить время жизни кэша не наугад, а до конца ближайшего окна.

## 7. Контракты API

### 7.1. Общие правила

- Версия в пути: `/api/v1/...` и `/api/v1/partner/...`.
- Единый формат ошибки для обоих API:

```json
{
  "code": "INSUFFICIENT_STOCK",
  "message": "Not enough stock for some items",
  "details": [{"menu_item_id": "...", "requested": 3, "available": 1}],
  "request_id": "01J..."
}
```

- Пагинация по курсору: `?cursor=...&limit=20`, в ответе `next_cursor`.
- Деньги: `amount_minor` (целое, копейки) + `currency`.
- Время: RFC 3339, UTC.
- Заголовки: `X-Client-Id` (публичный API), `X-Api-Key` (партнёрский),
  `Idempotency-Key` (обязателен для `POST /orders`).
- Выдача меню поддерживает условные запросы: `ETag` в ответе, `If-None-Match` в запросе,
  `304 Not Modified` при совпадении. Значение `ETag` строится из `venue_id` и `menu_version`
  (см. 6.6).

### 7.2. Публичный API

```
GET    /api/v1/venues                      # список, фильтры cuisine / is_open / q
GET    /api/v1/venues/{venueId}
GET    /api/v1/venues/{venueId}/menu       # позиции с флагом доступности и ценой акции
GET    /api/v1/rescue                      # сводная подборка «спасение остатков»
                                           # по всем заведениям, сортировка по ends_at

GET    /api/v1/cart
POST   /api/v1/cart/items
PATCH  /api/v1/cart/items/{itemId}
DELETE /api/v1/cart/items/{itemId}
DELETE /api/v1/cart

POST   /api/v1/orders                      # жёсткая проверка + резерв в одной транзакции
GET    /api/v1/orders/{orderId}
POST   /api/v1/orders/{orderId}/cancel
```

Недоступные позиции в меню **показываются с флагом**, а не скрываются: пользователь должен
понимать, что блюдо существует, но сейчас его нет.

### 7.3. Партнёрский API

```
GET    /api/v1/partner/venue
PATCH  /api/v1/partner/venue               # accepting_orders, min_order_amount, schedule

PUT    /api/v1/partner/menu                # полная синхронизация, upsert по external_id
POST   /api/v1/partner/menu/items
PATCH  /api/v1/partner/menu/items/{itemId}
POST   /api/v1/partner/menu/availability   # массово: стоп-лист и остатки

GET    /api/v1/partner/rescue-offers       # свои акции, ?active_only=true
POST   /api/v1/partner/rescue-offers       # создать акцию
DELETE /api/v1/partner/rescue-offers/{id}  # снять акцию досрочно

GET    /api/v1/partner/orders              # ?status=created&since=...   (поллинг)
POST   /api/v1/partner/orders/{id}/accept  # + eta_minutes
POST   /api/v1/partner/orders/{id}/reject  # + reason
POST   /api/v1/partner/orders/{id}/status
```

### 7.4. Исходящие вебхуки

`POST {venue.webhook_url}`, заголовки: `X-Signature` (HMAC-SHA256 от тела на секрете
партнёра), `X-Event-Id`, `X-Event-Type`. События: `order.created`, `order.cancelled`.

Пять попыток с нарастающей паузой. После — событие помечается `failed`; заведение всё равно
увидит заказ поллингом. Получатель обязан дедуплицировать по `X-Event-Id` — записать это
в README как часть контракта.

**Спеки пишутся до кода.** Хендлеры реализуют сгенерированные интерфейсы, а не наоборот.

## 8. Сервис-заведение (Go)

`external/venue-pasta-roma` — эмулятор собственной системы реального ресторана.

### 8.1. Правила изоляции (важно!)

Так как сервис на том же языке, есть соблазн переиспользовать код основного сервиса.
Этого делать нельзя — иначе интеграция перестаёт быть интеграцией и превращается в вызов
функции через HTTP. Жёсткие правила:

- **Отдельный `go.mod`.** В корне репозитория `go.work`, объединяющий оба модуля для
  удобства локальной разработки, но модули независимы.
- **Ноль импортов из `internal/` основного сервиса.** Проверяется `depguard`.
- Единственное, чем сервисы делятся, — файл `api/openapi/partner.yaml`. Из него генерируется
  **клиент** (`oapi-codegen` в режиме `client`). То есть эмулятор общается с платформой ровно
  так же, как это делал бы сторонний разработчик, у которого есть только спека.
- Свой Dockerfile, свой сервис в Compose, своё состояние (в памяти, без БД).

Побочная польза: если из спеки успешно генерируется рабочий клиент — значит, спека полная,
а не написана для галочки.

### 8.2. Поведение

1. На старте дожидается готовности платформы и загружает своё меню через
   `PUT /api/v1/partner/menu`, указывая собственные `external_id` у позиций.
2. Поднимает свой HTTP-API:
   - `POST /webhooks/orders` — принимает события от платформы, проверяет HMAC-подпись,
     дедуплицирует по `X-Event-Id`.
   - `GET /kitchen/orders` — лента «кухни», внутренний интерфейс ресторана.
     Это и есть «предоставляет свой API» из ТЗ.
   - `POST /kitchen/stock` — ручное изменение остатков, транслируется в платформу.
3. Получив `order.created`: если позиции не хватает — отклоняет, иначе принимает
   с оценкой времени. Дальше по таймеру двигает статусы
   `cooking → ready → delivering → delivered` через партнёрский API платформы.
4. Раз в 30 секунд синхронизирует остатки в платформу.

| `idempotency_keys` | Защита от дублей | `key`, `client_id`, `request_hash`, `order_id`, `expires_at` |
| `outbox_events` | Исходящие события | `aggregate_id`, `type`, `payload`, `status`, `attempts`, `next_attempt_at` |

Обязательные детали:

- Уникальный индекс `(venue_id, external_id)` на `menu_items` — это и есть связь с источником
  данных, о которой спрашивает ТЗ.
- Уникальный индекс `(client_id, key)` на `idempotency_keys`.
- **Запрет пересекающихся акций на уровне базы.** Включить расширение `btree_gist`
  и повесить на `rescue_offers` ограничение:
  `EXCLUDE USING gist (menu_item_id WITH =, tstzrange(starts_at, ends_at) WITH &&) WHERE (cancelled_at IS NULL)`.
  База сама не даст создать две пересекающиеся акции на одну позицию, даже при двух
  одновременных запросах. Это надёжнее проверки в коде и стоит отдельного абзаца в README.
- В `order_items` хранить `rescue_offer_id` (может быть NULL) — так видно, какая строка
  куплена по акции. Отчётность и разбор спорных заказов без этого невозможны.
- **Индексы под фактические фильтры каталога**, а не «на всякий случай». Проверить каждый
  через `EXPLAIN ANALYZE` и приложить вывод в README для двух-трёх ключевых запросов.
- **`venues.menu_version`** увеличивается на единицу в той же транзакции, что меняет меню,
  категории, цены, стоп-лист, остатки или акции. Пропущенное обновление счётчика приведёт
  к тому, что клиент будет получать `304` на изменившееся меню, поэтому на это нужен тест.
- Частичный индекс `outbox_events (next_attempt_at) WHERE status = 'pending'`.
- `CHECK`-ограничения на статусы и на неотрицательные суммы и остатки.
- **Копирование названия и цены в `order_items`** — заказ не должен меняться задним числом
  при редактировании меню. Обязательно объяснить это решение в README.
- **Списание остатка только внутри транзакции оформления заказа**, через
  `SELECT ... FOR UPDATE` по строкам `menu_items`, отсортированным по `id`. Сортировка нужна,
  чтобы два параллельных заказа брали блокировки в одном порядке и не встали в дедлок.
  Это ключевое место всего задания — описать его в README подробно.

## 10. Качество кода

### 10.1. `.golangci.yml`

Включить: `errcheck`, `govet`, `staticcheck`, `revive`, `gosec`, `gocritic`, `ineffassign`,
`unused`, `bodyclose`, `noctx`, `sqlclosecheck`, `rowserrcheck`, `sloglint`, `errorlint`,
`nilerr`, `contextcheck`, `depguard` (правила из 6.2 и 8.1), `misspell` с `locale: US`,
`gofumpt`, `goimports`.
Исключения — только для `internal/generated/**`.

### 10.2. Ошибки

- Доменные ошибки типизированы и несут код: `errs.New(errs.CodeInsufficientStock, ...)`,
  оборачивание через `%w`.
- Превращение доменной ошибки в HTTP-ответ происходит **в одном месте** — `adapter/http/httperr`.
  Хендлеры не должны знать, какой статус соответствует какой бизнес-ошибке.
- Никаких `panic` в рабочем коде. Middleware `recover` ловит панику, логирует и отдаёт 500.

### 10.3. Тесты

- **Юнит-тесты** (табличные): стейт-машина, расчёт суммы, проверка расписания, правила
  доступности, идемпотентность.
- **Интеграционные** (testcontainers + настоящий PostgreSQL):
  - полный путь оформления заказа;
  - **два параллельных заказа на последнюю единицу товара** — обязательный тест,
    он доказывает, что блокировки расставлены правильно;
  - повторный `Idempotency-Key`;
  - доставка вебхука и ретрай при ошибке;
  - `menu_version` растёт при каждом изменении меню, и `304` не возвращается на изменившееся
    меню.
- Домен и юзкейсы покрыть не ниже 70%. Адаптеры до 100% не гнать.

### 10.4. Эксплуатация

- Graceful shutdown по `SIGTERM`/`SIGINT` с таймаутом 10 секунд.
- `GET /healthz` (жив) и `GET /readyz` (готов, проверяет БД).
- Логи структурированные, с `request_id`, **без персональных данных** (телефон и адрес
  не логировать).
- Таймауты на всех исходящих HTTP-вызовах и на `http.Server`.
- Конфиг валидируется на старте: при некорректных значениях приложение падает сразу.

Строго такая структура:

1. **Что это** — 3–4 предложения.
2. **Быстрый старт** — `docker compose up`, ссылка на Swagger UI, готовые примеры `curl`

   зависимостей и то, что они проверяются линтером.
5. **Микросервисный вариант** — целевая схема, разбор саги резервирования остатков,
   что мешает разрезать сейчас, и порядок отделения сервисов: первым `integration`
   (у него нет транзакционной связности с остальными, граница уже проходит по outbox),
   вторым `catalog` (вот тут и появляется сага), последним `partner`.
6. **CJM** — обе диаграммы плюс текстовый разбор трудностей пользователя. Это прямой ответ
   на формулировку ТЗ «главная цель — составить анализ, как человек находит товар и с какими
   трудностями сталкивается».
7. **Схема БД** — ERD и разбор решений: копирование цены в `order_items`, `stock_qty NULL`,
   `external_id` как связь с источником данных, таблица идемпотентности.
8. **API** — как открыть спеки, чем отличаются публичный и партнёрский контуры, модель
   доступа и почему она не противоречит требованию «авторизация не нужна».
9. **Спасение остатков** — отдельный раздел про отличительную особенность площадки:
   какую проблему решает для заведения и для пользователя, как устроена модель, почему
   активность акции вычисляется, а не хранится, почему пересечение окон запрещено
   ограничением базы, а не проверкой в коде.
10. **Ключевые технические решения** — по абзацу на каждое: идемпотентность, защита от гонок
    при списании остатков, outbox, вебхук плюс поллинг, стейт-машина.
11. **События и брокер сообщений** — почему outbox нужен независимо от брокера (проблема
    двойной записи), контракт события, ключ партиционирования и почему это `order_id`,
    что именно изменится при переходе на Kafka (реализация `EventPublisher`, больше ничего),
    и почему брокер не поставлен сейчас. Тезис: готовность к масштабированию обеспечивают
    outbox, контракт и интерфейс; брокер — это уже само масштабирование, которое пока
    не требуется.
12. **Кэширование** — лестница решений с указанием, где мы находимся:
    - Ступень 0 (сделано): индексы, отсутствие N+1, курсорная пагинация, `ETag` и `304`
      через `menu_version`.
    - Ступень 1: кэш в памяти процесса, ловушка cache stampede и `singleflight`.
    - Ступень 2: Redis — при нескольких экземплярах приложения, необходимости пережить
      перезапуск, либо нужде в атомарных счётчиках и распределённых блокировках.
      Redis решает проблему **общего** кэша, а не **быстрого**.
    - Ступень 3: реплика для чтения, отдельная денормализованная модель чтения.
    - Отдельно и жирно: **что кэшировать нельзя** — доступность, стоп-лист, остатки,
      активность акций. Иначе площадка продаёт то, чего нет, и пользователь получает отказ
      в худший момент, после ввода адреса.
    - Инвалидация: outbox уже даёт готовый канал, изобретать новый не придётся.
13. **Допущения и упрощения** — честный список с обоснованиями.
14. **Точки роста**:
    - **Складчина.** Соседи по дому скидываются на один заказ, чтобы вместе перешагнуть
      минимальный чек. Пул открыт ограниченное время, позиции участников придерживаются
      мягким резервом со сроком жизни, при истечении окна резервы освобождаются и пул
      распадается. Заведение получает один заказ вместо нескольких мелких, курьер едет
      один раз. Технически это вторая стейт-машина, переходы в которой происходят
      по таймеру и по достижению суммы, а не по команде человека.
    - Автоматические правила акций: включать скидку за N часов до закрытия.
    - Вынос поиска в отдельный движок.
    - Шардирование заказов.
15. **Разработка** — цели Makefile, генерация кода, запуск тестов.
